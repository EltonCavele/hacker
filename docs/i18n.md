# Internationalization (i18n)

Languages: **Portuguese (`pt`)** and **English (`en`)**, via [`next-intl`](https://next-intl.dev). No URL prefix: the language lives in a cookie, so URLs, auth redirects and the PWA `start_url` stay the same for everyone.

## How the language is chosen

1. **The cookie `NEXT_LOCALE` wins.** Set by the language switcher (Settings → Language) for a year.
2. **No cookie (first visit):** `proxy.ts` detects the country **once** and stores the result in the cookie, so later requests never look at the IP again.
   - Country in `PT BR AO MZ CV GW ST TL GQ MO` → `pt`; anywhere else → `en` (the default).
   - Country source, in order: CDN header (`cf-ipcountry`, `x-vercel-ip-country`, `cloudfront-viewer-country`, `x-country-code`) → IP lookup (`GEOIP_URL`, 800 ms timeout, memoised per IP for 24 h) → `Accept-Language`.
   - A country match is stored for 1 year. If it falls back to `Accept-Language` (lookup failed), the cookie lasts 1 day so it is retried later.
   - Private/unknown IPs are never sent to the lookup service. The client IP comes from `getClientIp` (`lib/client-ip.ts`, honours `TRUSTED_PROXY_HOPS`).
3. `proxy.ts` also passes the detected locale to the first render in the `x-locale` request header (the cookie does not exist yet on that request). `i18n/request.ts` reads cookie → header → default.

Privacy: the IP lookup sends the visitor's IP to the provider in `GEOIP_URL`. Behind Cloudflare/Vercel the header is used instead and nothing leaves the app. Point `GEOIP_URL` at a self-hosted service if that matters.

## Where things live

| What                                                           | Where                                                                  |
| -------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Locales, cookie names, country list, formatting tags           | `lib/i18n/config.ts`                                                   |
| Country → locale detection (no per-render cost)                | `lib/i18n/detect.ts`, called from `proxy.ts`                           |
| Messages                                                       | `messages/en.json`, `messages/pt.json` (same keys; a test enforces it) |
| next-intl request config                                       | `i18n/request.ts`                                                      |
| Switch language (server action + select)                       | `lib/i18n/actions.ts`, `components/language-switcher.tsx`              |
| Locale/translator outside React (emails, push, route handlers) | `lib/i18n/server.ts`, `lib/i18n/translator.ts`                         |

`global.d.ts` types keys against `messages/en.json`, so a wrong `t("key")` fails `tsc`.

## Writing UI text

- Server Components / actions: `const t = await getTranslations("namespace")` (`next-intl/server`).
- Client Components: `const t = useTranslations("namespace")`. The root layout provides the messages.
- Plurals and rich text use ICU: `"{count, plural, one {# item} other {# items}}"`, `t.rich("key", { strong: (c) => <strong>{c}</strong> })`.
- Dates/numbers: format with `FORMAT_LOCALE[locale]` (`useLocale()`), never a hard-coded tag.
- Adding a string = add the key to **both** JSON files. Adding a language = add it to `locales`, `FORMAT_LOCALE`, a `messages/<code>.json`, the switcher names, and `PORTUGUESE_COUNTRIES`-style mapping in `detect.ts` if it should be auto-selected.
- Emails/push have no React context: read the locale with `getRequestLocale()` _inside the request_ (before any fire-and-forget) and use `getTranslator(locale)`.

Not translated: the dev-only `/design-system` page, server log messages, and API error codes.
